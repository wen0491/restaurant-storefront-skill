# 餐饮门头焕新 Skill

交付用于讨论品牌表达和门面设计方向的概念图，以及可追溯的需求、提示词、检查和修改记录。优先保证现场条件与文字准确，再追求审美完成度。概念图不证明尺寸、结构、消防、招牌审批或施工可行性。

## 1. 形成最小需求单

读取 [需求单模板](assets/brief-template.md)，从用户已有信息填起。首轮只补问影响生成的少量问题：业态与准确店名；现场硬约束；参考方向、画幅和视角。能从附件读出的内容先观察，避免让用户重复描述。

用户提供标注方案和素材目录时，先从资料提取区域、材质和保留内容，提出对应关系让用户纠正。用户负责设计标准和最终审美认可；Agent负责资料整理、提出适配方式、执行图片编辑和核验。修改范围或职责尚不明确时，先达成约定再生图；已有明确规则时直接沿用，不重复访谈。核心设计交付为图片，过程文档只用于追溯，不默认排成PDF或整套方案。

每条需求标记来源：用户明确提供／照片观察／设计假设／待确认。照片推断不当作实测；看不清的字、被遮挡的入口和侧面保持未知。

分清两种工作：
- **有现状的改造**：现状图是几何依据，风格参考仅提供指定的色彩、材料、招牌或氛围。按用户要求锁定建筑轮廓、开口和周边环境。
- **无现状的探索**：可以提出设计假设，交付注明“虚构场地概念”。不声称适配真实商铺。

用户做品牌复制店、同品牌多店或固定区域换材时，另读 [品牌复制店规则](references/brand-replication.md)。品牌层只复用有资料依据的材质、区域映射和视觉表达；每家店的几何与镜头由当次输入决定。品牌具体数据保存在项目的品牌档案中，不写成所有餐饮店通用的风格。

关键文字、图片角色或不可变的开口存在冲突时，先提出一个合并问题，继续整理不依赖答案的部分。其他未知项可采用明确标注的假设。已有足够信息且用户已授权生图时直接继续，不额外要求确认整张表。

完成条件：形成一份有来源的需求单，硬约束可逐项核对，剩余未知项不会被包装为已知现场条件。

## 2. 把审美转成可观察的设计要求

首次使用或出现风格偏差时读 [设计与参考图规则](references/design-rules.md)。提取参考图中真正要借用的特征，写出简短设计说明：业态和客群表达、招牌与入口层级、材料及色彩关系、灯光和街道尺度。

将“高级、年轻、烟火气”等词转为具体视觉选择。保留用户自己的审美表达；未提供偏好时提出一个合理方向并标记为假设。第一版只做一个方向、一张主图，不擅自扩成全套品牌或室内项目。

建立从画面左到右的立面顺序，例如“窗洞 W1 → 门洞 D1 → 窗洞 W2”。区分门洞数、门扇数、窗洞数和玻璃分格数。第一张优先采用能核验开口的视角；如用户指定透视角度，记录遮挡导致的核验限制。

完成条件：设计说明与硬约束兼容，参考图各自的用途明确，不将风格图的店名和结构带入本案。

## 3. 生成或编辑一张主图

真正生成或编辑图片前，读取当前环境的 **imagegen** 技能，使用其内置 image_gen 工具。工具不可用时保留需求与提示词，明确“图片未生成”，不以网页、代码图或素材图充当效果图。

本地输入图先用 view_image 查看。记录附件次序、文件路径及各自角色；对现状图进行保留结构的改造按编辑处理。参数使用当前工具支持的字段，不把提示词中的画幅当作工具已保证的像素规格。

将最终实际提交的完整提示词保存为 `prompt-v01.md`。提示词依次包含：
1. 用途及新建/编辑意图；
2. 图像角色和参考范围；
3. 建筑几何、开口顺序、入口及保留部位；
4. 业态表达、材料、色彩和灯光；
5. 招牌逐字原文、阅读顺序与位置；
6. 视角、画幅、完整门面取景；
7. 本次修改范围及必须保留的条件。

只使用需求单中的招牌内容，避免自行添加年份、英文名、宣传语。优先让门面、招牌和入口完整可见，以便检查。现状照片中无法确定的部位不声称得到准确复原。

生成结果按 `storefront-v01.png`、`storefront-v02.png` 等版本保存到案例目录，保留失败版本。记录真实工具返回路径、调用方式和原始像素尺寸；尺寸放大与原生输出分开记载。不得仅因工具调用成功就标记验收通过。

## 4. 看图检查、针对性修改

每一版都读取 [验收与迭代规则](references/acceptance.md)，使用 [检查记录模板](assets/review-template.md)。实际打开输出，并与需求单和现状图逐项对照。看不清的项标记“无法判断”。

硬约束任一项不通过或无法判断，都不能报告整体验收通过。没有现状依据时，现场保真项标记“不适用：无现状依据”，仍核对已声明的概念布局。

发现问题时：记录具体位置和实际表现 → 针对最重要的一类问题编辑 → 在提示词中重申其余不变量 → 重查全部硬约束，防止修字后入口发生漂移。默认初稿后最多做两轮修订；用户另有要求时按其要求。仍失败则保留未通过版本、说明工具限制和下一步，不循环重抽碰运气。

客观核验和用户审美认可分别记录。可以报告“硬约束自检通过，审美待用户反馈”，不能代替用户接受设计方向。

## 5. 完成交付与事实记录

每个案例交付：
- 填好的需求单和简短设计说明；
- 实际使用的各版提示词、对应图片及版本检查记录；
- 选定版本或明确的未通过结论；
- 仍未知的现场条件、未解决问题和概念图边界。

最终回复展示主图并给出本地文件链接，注明是否通过、哪些项未核验、使用了内置 image_gen 还是获准的其他路径。仅有提示词时，交付状态为“需求与生成要求已完成”。

测试记录区分文件结构校验、无生图的流程推演、真实生图自检、用户反馈。一个案例通过只证明该案例，不能推出所有餐饮业态或现状照片都适用。简历与作品集只引用已有文件及真实测试，不虚构用户量、效率数据或施工能力。

需要示范填写方式时读 [虚构示例](references/example.md)；示例不是默认客户需求，也不是已通过的生成案例。
